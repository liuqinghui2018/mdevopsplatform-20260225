# 铁路电务智能化数据中台总体方案

## 1. 项目背景

面向铁路行业“电务智能化数据中台”建设场景，需将约 30 个业务系统的数据统一汇聚到中台，支撑实时数据接入、集中存储、统一治理、共享服务和后续智能分析，并满足国产信创环境要求。

## 2. 核心约束与设计原则

### 2.1 核心约束

- 接入范围：约 30 个业务系统
- 数据特征：同时覆盖实时数据与离线批量数据
- 环境约束：需兼容国产信创数据库、国产 CPU、国产操作系统
- 规模目标：按年规模 200T 进行容量规划

### 2.2 设计原则

- **统一接入**：统一标准、统一接口、统一采集链路
- **实时优先**：支持秒级接入、分钟级处理、准实时共享
- **分层解耦**：采集、传输、存储、治理、服务、运维安全分层建设
- **信创适配**：优先采用已完成国产化适配验证的软硬件组件
- **弹性扩展**：满足后续新增系统、数据主题与算法场景扩容
- **安全可控**：全链路审计、分级授权、脱敏与容灾并重

## 3. 总体架构

### 3.1 分层架构

#### （1）数据采集层

负责接入各业务系统的数据，支持以下模式：

- 数据库 CDC 增量采集
- API/文件离线同步
- 设备与监测系统消息接入
- 日志与事件数据采集

#### （2）实时传输层

负责实时数据缓存、分发和削峰填谷：

- 建立统一消息总线
- 支持主题隔离、顺序消费、重试补偿
- 支撑实时指标计算、告警联动和异步解耦

#### （3）存储计算层

围绕不同类型数据构建统一存储与计算底座：

- 关系型库承载主数据、配置数据、共享服务库
- 分布式分析型存储承载明细、主题、汇总分析
- 对象存储或归档存储承载历史冷数据、备份数据
- 批流一体计算支撑离线加工与实时处理

#### （4）数据治理层

统一管理数据标准、元数据、血缘、质量和安全：

- 数据标准管理
- 主数据管理
- 元数据与血缘管理
- 数据质量监测
- 权限控制与审计追踪

#### （5）服务层

对内对外提供统一数据服务能力：

- 主题数据服务
- 实时指标服务
- 数据共享 API
- 报表查询服务
- 告警事件服务

#### （6）运维安全层

保障平台持续稳定运行：

- 平台监控
- 日志审计
- 资源管理
- 备份恢复
- 双机/集群高可用
- 灾备演练

### 3.2 逻辑链路

业务系统/设备数据 → 统一采集 → 消息总线/离线同步 → ODS 明细层 → 主题建模与治理 → 实时/离线计算 → 数据服务/API/报表/告警输出

## 4. 数据接入策略

### 4.1 分类接入策略

| 数据类型 | 接入方式 | 时效目标 | 适用场景 |
| --- | --- | --- | --- |
| 实时交易/状态数据 | CDC + 消息总线 | 秒级到分钟级 | 调度状态、设备状态、告警事件 |
| 半实时业务数据 | 微批同步 | 5~15 分钟 | 统计汇总、经营分析 |
| 历史批量数据 | 定时抽取/文件同步 | 小时级到天级 | 历史补录、专题分析 |
| 非结构化数据 | 文件/对象接入 | 按业务周期 | 日志、图片、检测附件 |

### 4.2 统一标准

- 统一数据编码规范：系统编码、设备编码、站段编码、线路编码
- 统一主数据体系：组织、设备、人员、地点、资产、工单等核心对象
- 统一接口规范：字段命名、时间格式、状态枚举、增量标识、错误码
- 统一交换规范：接口鉴权、重试机制、幂等控制、异常告警

### 4.3 接入治理要求

- 新系统接入前完成数据摸底与字段映射
- 接入上线前完成质量校验和主数据比对
- 接入后纳入统一监控、审计和变更管理

## 5. 技术选型建议

### 5.1 选型原则

- 优先选择支持国产 CPU、国产操作系统的成熟产品
- 优先选择具备大规模生产案例和运维能力的组件
- 优先选择支持高可用、扩展性和生态兼容的方案

### 5.2 推荐技术栈方向

| 能力域 | 建议方向 |
| --- | --- |
| 操作系统 | 银河麒麟、统信 UOS 等国产操作系统 |
| CPU/服务器 | 鲲鹏、海光、飞腾等国产 CPU 服务器 |
| 关系型数据库 | openGauss、OceanBase、达梦等信创兼容数据库 |
| 消息中间件 | RocketMQ、Pulsar 或完成信创适配验证的消息平台 |
| 实时计算 | Flink 类流处理引擎或已完成适配验证的同类产品 |
| 批量计算 | Spark/分布式计算框架或国产兼容发行版 |
| 分析型存储 | MPP/湖仓一体方案或国产兼容分析引擎 |
| 元数据治理 | 统一数据目录、血缘、质量管理平台 |
| 可视化服务 | BI 报表平台、统一服务门户、API 网关 |
| 运维监控 | 指标监控、日志平台、链路追踪、统一告警 |

### 5.3 选型落地建议

- 关键组件必须完成国产 CPU + 国产 OS + 国产数据库兼容性验证
- 建议优先做 PoC，验证写入性能、实时延迟、故障切换和运维复杂度
- 对数据库、中间件、计算引擎统一输出适配清单和兼容矩阵

## 6. 存储体系设计

### 6.1 分层存储模型

| 层级 | 说明 | 保存策略 |
| --- | --- | --- |
| ODS 明细层 | 原始接入数据，保留原貌 | 保留完整明细，支撑追溯 |
| DWD 主题明细层 | 清洗、标准化、统一编码后的明细数据 | 支撑主题分析与应用复用 |
| DWS 汇总层 | 业务指标、宽表、专题数据集 | 支撑报表、驾驶舱、专题分析 |
| ADS 应用层 | 面向应用服务的数据集市 | 支撑接口服务、场景应用 |
| Archive 归档层 | 冷数据、历史备份、长期留存 | 降低主存储成本 |

### 6.2 存储策略

- 高频查询数据保存在高性能分析存储中
- 实时写入数据通过消息缓冲 + 流式落库方式承载
- 历史低频数据按月或按年归档到低成本存储
- 重要业务数据按照业务主题和时间双维度分区

### 6.3 数据生命周期

- 近 3~6 个月：在线热数据
- 6~24 个月：近线数据
- 24 个月以上：归档数据
- 关键监管数据按制度要求长期保存

## 7. 实时能力设计

### 7.1 实时场景

- 设备状态实时采集
- 关键指标实时计算
- 异常事件实时识别
- 阈值告警与联动通知
- 实时看板与运行态势展示

### 7.2 实时处理链路

实时接入 → 消息缓冲 → 流式清洗 → 维表关联 → 指标计算 → 告警规则匹配 → 实时库/缓存/API 输出

### 7.3 关键能力要求

- 支持秒级采集与消费
- 支持断点续传和消息重放
- 支持幂等写入与乱序处理
- 支持实时任务高可用和故障自动恢复

## 8. 数据治理体系

### 8.1 数据质量

- 完整性校验
- 唯一性校验
- 合法性校验
- 一致性校验
- 时效性校验

### 8.2 元数据与血缘

- 建立表、字段、接口、任务、报表的统一元数据目录
- 跟踪从源系统到指标报表的全链路血缘关系
- 支撑影响分析、问题定位和变更评估

### 8.3 标准与主数据

- 建立统一数据标准库
- 建立统一主数据编码中心
- 统一业务口径、指标定义、数据字典

### 8.4 权限与审计

- 按组织、角色、数据域进行授权
- 对敏感字段进行脱敏或分级开放
- 对查询、下载、共享、变更进行全程审计

## 9. 容量与性能评估

### 9.1 规划口径

当前输入同时出现“每天新增 2G 数据”和“年规模 200T”两个口径，二者不一致：

- 2G/天约为 0.73T/年
- 年规模 200T 显著高于按天测算结果

因此建议采用以下方式规划：

- **近期建设口径**：按当前日常增量规模设计性能与吞吐
- **中长期容量口径**：按年规模 200T 进行存储与扩展规划

### 9.2 容量建议

按年 200T 规划，考虑副本、索引、临时空间、治理加工与备份开销，建议：

- 在线生产存储：不少于 300T 可用容量
- 备份与归档存储：不少于 300T 可用容量
- 总体存储规划：建议首期预留 600T 级别空间，并支持横向扩容

### 9.3 性能建议

- 实时链路按高峰突发量进行容量校核
- 采集与计算节点均支持横向扩展
- 核心组件部署高可用集群，避免单点故障
- 关键服务设置容量阈值、延迟阈值、堆积阈值告警

## 10. 实施路径

### 第一阶段：底座建设

- 完成信创环境适配验证
- 部署数据库、消息总线、计算与存储底座
- 建立统一采集标准、编码标准和安全规范

### 第二阶段：重点系统接入

- 优先接入关键业务系统和高价值实时场景
- 建设 ODS、主题域、主数据和基础服务能力
- 建立统一监控和质量校验机制

### 第三阶段：实时场景落地

- 建设实时指标、实时告警、实时看板能力
- 打通事件联动、接口共享和业务闭环

### 第四阶段：治理完善

- 完善元数据、血缘、质量、权限和审计
- 推进标准统一和跨系统数据协同

### 第五阶段：全量推广

- 完成全部系统接入
- 覆盖更多专题分析与智能应用场景
- 建立持续运营与迭代优化机制

## 11. 风险清单

| 风险项 | 风险说明 | 应对措施 |
| --- | --- | --- |
| 信创适配风险 | 组件在国产环境兼容性不足 | 提前开展 PoC 和兼容性测试 |
| 数据标准不统一 | 多系统口径不一致 | 先行建设数据标准和主数据体系 |
| 实时链路拥塞 | 高峰流量导致堆积 | 引入消息缓冲、弹性扩容和限流机制 |
| 历史数据质量差 | 补录和迁移数据存在缺失或异常 | 制定专项清洗与校验方案 |
| 运维复杂度高 | 多组件协同运维困难 | 建立统一监控、自动化运维和应急预案 |

## 13. 结论

本方案以“统一接入、实时支撑、分层治理、信创适配、弹性扩展”为主线，适用于铁路电务智能化数据中台建设。实施时建议优先完成信创适配验证、标准体系建设和重点实时场景落地，在保证稳定性的前提下逐步完成 30 个业务系统全量接入，并以年规模 200T 作为中长期扩展基线。
